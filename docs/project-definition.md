# Project Definition

## 1. Project Overview

**Project:** Classic Pong
**Repository:** classic_pong_project
**Engine:** Godot
**Programming Language:** C#
**Development Environment:** Visual Studio Code
**Version Control:** Git / GitHub
**Project Management:** Trello

Classic Pong is an educational game development project focused on learning and practicing programming with C# and the development of 2D video games.

The project uses Pong as a small and manageable scope through which to practice a complete software development lifecycle, from project definition and requirements through development, testing, release, and retrospective.

The initial goal is to recreate the core experience of classic Pong. Once that version is stable, the project may be extended with original modifications while keeping the overall scope controlled.

---

## 2. Project Objectives

The main objective is to create a playable and stable version of Pong.

The project also aims to practice:

* Programming with C# in a practical context.
* Game development with Godot.
* System design and decomposition.
* Problem solving.
* Reasoning about program logic before implementation.
* Working with variables, conditions, methods, objects and other programming concepts as they become necessary.
* The software development lifecycle (SDLC).
* Version control and incremental development with Git.
* Manual testing, debugging and regression.
* Technical decision-making and refactoring.

The project is not intended to demonstrate mastery of C# or advanced game development techniques. C# will be used as the programming tool required to build the game.

---

## 3. Learning Approach

The project will follow a learning-by-doing approach.

Implementation will be performed by the developer, with guidance during the reasoning, design and problem-solving process.

When a programming problem requires a concept or tool that is not yet familiar, that concept will be learned in the context of the problem rather than introduced independently without a practical need.

Solutions should seek an appropriate balance between:

* Simplicity.
* Readability.
* Efficiency.
* Maintainability.
* Technical complexity.

The project should avoid both unnecessary complexity and unstructured or difficult-to-maintain code.

The objective is to progressively improve the quality of solutions as the project develops.

---

## 4. Development Process

The project will follow an SDLC adapted to the scale of a small game.

The general process will be:

1. Project definition.
2. Requirements analysis.
3. Game and system design.
4. Planning.
5. Implementation.
6. Testing.
7. Bug fixing and refinement.
8. Release.
9. Retrospective and documentation of the development process.

The process will be iterative rather than strictly linear. Decisions and implementations may be revisited when testing or development reveals problems or better solutions.

---

## 5. Quality Approach

The objective is not merely to make the game technically functional.

The final result should feel like a solid small project: playable, stable, functional and reasonably maintainable, without pursuing unnecessary perfection.

Testing will be performed throughout development rather than only at the end.

Errors should be identified and corrected as early as reasonably possible in order to reduce the cost and complexity of later corrections.

The distinction between **working** and **done** will be maintained.

A feature being implemented does not necessarily mean that it is finished. It should also be tested and validated before being considered complete.

---

## 6. Version Control and Traceability

Git and GitHub will be used throughout the development process.

Development will be incremental rather than performed locally and uploaded only after the game is finished.

Whenever practical, the workflow will follow:

**Task → Implementation → Testing → Correction → Validation → Commit**

The Git history should provide a useful representation of the project's evolution.

Development decisions, relevant problems, solutions and learning outcomes should be documented when they provide value for future development or for understanding the project's process.

---

## 7. Documentation Principles

Documentation will be maintained as part of the project, but it should remain proportional to the project's size.

Documents should have a clear purpose and should help either:

* develop the project;
* maintain or resume the project;
* understand decisions and results; or
* communicate the development process.

The documentation should allow the project to be resumed after a significant interruption by providing enough context to understand:

* what the project is;
* what has already been done;
* what remains to be done;
* which important decisions were made;
* which problems were encountered; and
* where development should continue.

The development process will also be documented as a practical record of the project rather than as a purely formal exercise.

---

## 8. Scope Principles

The project must remain small enough to be completed.

The intended scope is limited to a Pong experience with:

* Player versus AI.
* Local player versus player.

Online multiplayer is outside the scope of this project.

More ambitious ideas for other variations of Pong may be considered for future projects rather than incorporated into Classic Pong.

The project should prioritize completion and a solid final result over adding a large number of features.

---

## 9. Portfolio Purpose

The project has a secondary portfolio purpose.

The objective is not to present the project as professional commercial game development, but to demonstrate the ability to take a small software project through a structured development process.

The repository should make it possible for another person to understand the development workflow, including relevant decisions, implementation, testing, problems and solutions.

The final project should therefore provide evidence of both the resulting game and the development process behind it.

---

## 10. Project Success Criteria

The project will be considered successful when it achieves its educational and development objectives.

At minimum, the completed project should demonstrate:

* A stable and playable Pong implementation.
* A complete development process from definition to release.
* Practical use of C# and Godot.
* Incremental development using Git.
* Testing and bug correction throughout development.
* Reasonable technical and design decisions.
* Documentation sufficient to understand and resume the project.
* A distributable build that can be tested by people other than the developer.
* A clear record of the development process suitable for portfolio presentation.
